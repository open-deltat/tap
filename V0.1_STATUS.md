# TAP v0.1 Implementation Status

## ✅ COMPLETED

### Core Domain & Storage
- ✅ Bitmap allocator (in-memory, per resource/day)
- ✅ Real concurrency control (mutex per resource/day)
- ✅ Hold expiry mechanism (`expireHolds` function)
- ✅ Domain schemas (Tenant, Resource, Offer, Hold, Booking, LedgerEvent)
- ✅ Resource fields: timezone, slotMinutes, horizonDays, requiresPayment, metadata
- ✅ Postgres event store (`ledger_events` table)
- ✅ Event sourcing (append-only ledger)

### API Surface
- ✅ Public endpoints:
  - ✅ `GET /v1/public/:tenantSlug/:resourceSlug/availability`
  - ✅ `POST /v1/public/:tenantSlug/:resourceSlug/book`
- ✅ Private endpoints:
  - ✅ `GET /v1/availability`
  - ✅ `POST /v1/holds`
  - ✅ `POST /v1/bookings`
  - ✅ `GET /v1/events`
- ✅ Basic health endpoint (`/health`)

### Error Handling
- ✅ Protocol-wide error system (`@tap/errors` package)
- ✅ All 15 error codes defined and tested
- ✅ Structured error responses

### Core Functionality
- ✅ Place hold
- ✅ Confirm booking
- ✅ Cancel booking (core function exists)
- ✅ Expire holds (function exists)

## ❌ MISSING (Critical for v0.1)

### 1. Horizon Limits Enforcement
- ❌ Allocator doesn't enforce `horizonDays` limit
- ❌ API doesn't reject bookings beyond horizon
- **Impact**: Users can book arbitrarily far in the future

### 2. Offer Entity Integration
- ❌ Offer schema exists but not used
- ❌ Availability calculation doesn't use Offers (base availability)
- ❌ No Offer persistence/storage
- ❌ No API endpoints for managing Offers
- **Impact**: Can't set opening hours, pricing rules

### 3. Booking Cancellation API
- ❌ Core has `cancelBooking()` but no API endpoint
- ❌ Missing: `POST /v1/bookings/:id/cancel`
- **Impact**: Can't cancel bookings via API

### 4. Hold Expiry Background Worker
- ❌ `expireHolds()` exists but not running as background process
- ❌ No scheduled tick (every 1-5 seconds)
- **Impact**: Holds never expire automatically

### 5. Resource/Offer Persistence
- ❌ Only events are persisted to Postgres
- ❌ No `tenants`, `resources`, `offers`, `bookings`, `holds` tables
- ❌ Resources registered in-memory only
- **Impact**: Data lost on restart, can't query resources

### 6. Auth & Security
- ❌ No JWT authentication
- ❌ No rate limiting
- ❌ No quotas/abuse guards
- ❌ No per-tenant limits (maxHoldsPerMinute, etc.)
- ❌ No IP-based rate limiting for public API
- **Impact**: No security, vulnerable to abuse

### 7. Idempotency
- ❌ No `Idempotency-Key` header support
- ❌ No idempotency tracking
- **Impact**: Duplicate requests can create duplicate bookings

### 8. Google Calendar Integration
- ❌ No OAuth2 flow
- ❌ No calendar adapter
- ❌ No one-time import (GCal → TAP)
- ❌ No one-way mirror (TAP → GCal)
- **Impact**: Can't sync with Google Calendar

### 9. Payment Integration
- ❌ Payment fields exist in schema but no actual payment flow
- ❌ No Stripe integration (even placeholder)
- ❌ No payment webhook handling
- **Impact**: Can't handle paid bookings

### 10. Admin UI
- ❌ No admin interface
- ❌ No resource management UI
- ❌ No booking management UI
- ❌ No Google Calendar connection UI
- **Impact**: Can't manage resources/bookings via UI

### 11. Public Booking UI
- ❌ No public booking page (`/book/:tenantSlug/:resourceSlug`)
- ❌ No embeddable widget
- **Impact**: Can't provide public booking links

### 12. Status/Health Endpoint Enhancement
- ⚠️ Basic `/health` exists but missing:
  - ❌ `dbStatus` check
  - ❌ `last ledger_events.event_id per tenant`
  - ❌ `buildId`
